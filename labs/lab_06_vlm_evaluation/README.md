# Лабораторная работа №6. Оценка VLM: качество, ошибки и абляция

**Дата:** 26.10.2026
**Ноутбук:** [student.ipynb](student.ipynb) — выполнен полностью, `FAST_DEV_RUN = False`

## Постановка

Оценить открытую VLM на реальных изображениях четырёх типов задач: подписи, открытые вопросы, вопросы по документам, подсчёт с ответом в JSON. Вручную разметить ошибки и сравнить варианты prompt, разрешения и декодирования на одном наборе изображений.

## Данные и модель

- 20 изображений PixMo (allenai, ODC-BY-1.0; права исходных изображений могут отличаться), по 5 на задачу: pixmo-cap, pixmo-ask-model-anything, pixmo-docs, pixmo-count. Состав зафиксирован в `eval.jsonl`.
- SmolVLM2-2.2B-Instruct, LLM в NF4 (bitsandbytes, 1,33 ГБ), Apple MPS. Основная конфигурация: prompt без инструкций, длинная сторона 1536, greedy.

## Анализ ошибок

- Подсчёт: промахи на 1–7 объектов; в vqa-6 модель считает все прутья каркаса вместо стержней на правой панели.
- JSON: одинарные кавычки, лишние вложенные ключи, числа строками. Инструкция «be concise» при 1536 вообще заменяет JSON голым числом, хотя 2 числа из 5 верны.
- Галлюцинации в подписях: выдуманные шкалы приборной панели, перепутанные цвета персонажа. Все подписи обрезаны лимитом 256 токенов.
- Метрики: EM и F1 на развёрнутых эталонах измеряют длину и форму ответа. EM открытых вопросов равен 0, хотя 2 ответа из 5 верны.

## Выводы

1. Модель хорошо читает документы при высоком разрешении и плохо считает объекты.
2. Без ручной разметки автоматические метрики искажают картину: форма ответа влияет на EM сильнее, чем правильность.
3. Краткая инструкция улучшает EM коротких ответов, но ломает JSON-формат, поэтому формат надо проверять отдельно.
4. Разрешение 1536 необходимо для документов (EM ×2–3) ценой в 11 раз большего числа входных токенов.

Ограничения: 5 примеров на задачу (шаг метрики 0,2), один разметчик; задержку измеряли при параллельной нагрузке на GPU.
